# World overhaul — аудит и план

Ветка: `feature/world-overhaul`. Дата аудита: 2026-11-16. Старая процедурная карта (`game/world/world_gen.gd`) **не удаляется**:
она остаётся как «legacy»-мир (сценарии с `"world": "procedural"`, старые сохранения, тесты) до полной проверки новой.

## 1. Аудит текущего проекта

| Область | Состояние |
|---|---|
| Код | ~5.5 тыс. строк GDScript: `simulation.gd` (≈2950), `main.gd` (≈1400), `scenario_editor.gd` (≈600), `map_view.gd`, `world_gen.gd` |
| Тесты | 1546 headless-проверок, CI зелёный на `main` |
| Карта | Процедурная 240×120, 160 провинций (130 суша + 30 море), 8 вымышленных стран |
| Сохранения | `var_to_str`, версия 10; мир не хранится, а **пересоздаётся из seed** |
| Рендер | Растровая карта (`cell_prov` на пиксель), границы считаются полным проходом по растру при каждом изменении |
| Производительность (baseline) | setup 290 мс, **6.5 мс/день** (160 провинций, 8 стран), 25 МБ статической памяти |

### Что симуляция требует от «провинции»
Симуляция работает с `world["provinces"][id]` и ключами `land`, `terrain`, `pop`, `industry`, `deposits`, `neighbors`, `land_neighbors`;
рендер — с растром `world["cell_prov"]`, `world["prov_cells"]`, `world["elev"]`, `w`, `h` и `center`. Остальное (армии, снабжение, ИИ, торговля,
авиация, политика, разведка) использует только числовой id провинции и массив `owner[]`.
**Вывод:** территориальные ячейки реального мира можно подать через тот же интерфейс (id ячейки = id «провинции»), не переписывая
экономику, дипломатию, ИИ, технологии, события и сценарии. Новая модель — это новый поставщик `world` + разделение понятий владения.

### Узкие места при масштабировании (160 → ~17 000 провинций, 8 → ~200 стран)
- `country_provinces()` и ~25 циклов по `owner.size()` — O(N) на вызов → нужны кеши списков по странам.
- `_supply_dist()` обходит всю доступную сушу для каждой страны с армией каждый день → ограничить радиус, считать не каждый день.
- `_rebuild_overlays()` в `map_view.gd` проходит по всему растру → заменить на чанки с инкрементальным обновлением.
- `checksum()` сериализует весь `owner[]` через `var_to_str` каждый вызов → нужен инкрементальный хеш (важно для мультиплеера).
- `from_dict()` пересоздаёт мир из seed → для реального мира нужен идентификатор набора данных + хеш.

### Зависимости мультиплеера от карты
1. Идентификаторы ячеек должны быть **стабильны** между платформами и версиями → набор данных версионируется и хешируется (`world_hash`), хеш входит в рукопожатие и контрольную сумму.
2. Команды ссылаются на id ячеек → формат id и порядок сортировки фиксированы в контракте (см. §4).
3. Синхронизируются только изменяемые данные (`owner/controller`, армии), а не геометрия.
4. Загрузка данных детерминирована и не зависит от платформы (бинарный формат с явным порядком байт).

## 2. Решения

### Источники данных (подробно — `docs/DATA_SOURCES.md`)
Natural Earth 10m (общественное достояние): страны, области (admin-1), спорные территории, озёра, реки, порты, аэропорты, дороги, железные дороги,
географические регионы. GeoNames `cities5000` (CC BY 4.0): населённые пункты с альтернативными названиями и населением.
Terrain Tiles (AWS Open Data, Mapzen/Tilezen; SRTM/GMTED/ETOPO и др., требует атрибуции): высоты.

### Иерархия территорий
`WORLD → COUNTRY → REGION → DISTRICT → SETTLEMENT → CELL`
- COUNTRY — Natural Earth admin-0 (суверенные государства и зависимые территории; `SOVEREIGNT` задаёт суверена).
- REGION — Natural Earth admin-1 (≈4.6 тыс.). Для стран без admin-1 регион = страна.
- DISTRICT — **геометрии районов в открытых глобальных данных, пригодных для игры, нет** (Natural Earth не содержит admin-2). Районы представлены
  атрибутом населённого пункта (admin-2 из GeoNames), без полигонов. Это ограничение зафиксировано честно.
- SETTLEMENT — GeoNames `cities5000` (≈50 тыс.). Сёла менее 5000 жителей в репозиторий не входят; инструмент `tools/world/build_world.py`
  умеет собрать `cities1000/cities500` локально.
- CELL — военные ячейки (≈1° по площади), вложены в регионы, но **независимы от административных границ как система контроля**.

### Владение, контроль, претензии, игровой контроль
Четыре разных понятия (в сохранении — четыре отдельных массива/набора):
1. `legal[]` — международно признанная принадлежность на дату сценария (по Natural Earth `SOVEREIGNT`; спорные территории — отдельный слой).
2. `owner[]` (**игровой контроль**, он же «controller» в симуляции) — меняется только действиями армий.
3. `claims` — претензии (спорные территории Natural Earth, датированный слой).
4. Фактический контроль на дату сценария — начальное значение `owner[]`, может отличаться от `legal[]` для спорных/оккупированных районов (по данным, которые удалось подтвердить, и с пометкой достоверности).

### Постепенный захват
Захват меняет контроль **одной ячейки** (`owner[cell]`); регион остаётся смешанным. Передача больших территорий возможна только отдельным правилом
капитуляции/мирного договора (`legal[]` меняется только там).

## 4. Общий контракт данных (для Windows/Android-разработчика)
- Файлы набора данных лежат в `data/world/`; формат — little-endian, массивы типизированные; описание полей — `data/world/README.md`.
- ID ячеек: целые `0..N-1`, **суша — первой (по возрастанию region_id, затем порядок построения), море — после**. Порядок детерминирован скриптом сборки.
- Версия: `world_version` + `world_hash` (SHA-256 содержимого); любое изменение набора = новая версия.
- Запрещено создавать независимые системы провинций; любые правки геометрии — через `tools/world/build_world.py` и PR.

## 5. Риски и ограничения
- Размер репозитория: бинарный набор данных — десятки МБ; при росте — Git LFS.
- Точность: Natural Earth 10m (масштаб 1:10 000 000) — границы и берега генерализованы; растр ячеек 0.2° ≈ 22 км на экваторе.
- Спорные и быстро меняющиеся территории представлены на дату данных; это **не** заявление о правовом статусе.
- Исторические слои требуют отдельных источников; в этом PR их нет (см. статус фаз).
